# 具身智能任务编排统一实验协议 v1.0

版本：v1.0
制定日期：2026-08-28
适用范围：A/B/C/D 具身智能任务编排系统的 Baseline、消融实验、完整回归和比赛材料

机器可读配置：`testdata/benchmark/experiment_protocol_v1.json`

## 1. 为什么要建立统一实验协议

统一实验协议用于回答四个问题：

1. 我们到底和什么方案比较；
2. 所有方案是否在相同条件下比较；
3. 完整系统的提升来自哪个模块；
4. PPT 中的每一个数字能否被原始记录复现。

没有统一协议时，常见问题是：

- Baseline 使用固定规则，完整方案使用大模型，测试集却不一致；
- 一组结果来自 Mock，另一组结果来自 Isaac Sim，直接比较成功率；
- 只展示 64/64 或 40/40，不区分模块成绩和全链路成绩；
- 失败、阻断和安全停止被混成一个“失败率”；
- 为了提高结果临时修改测试样例、提示词或重试次数；
- PPT 中的指标无法回溯到具体案例和原始日志。

统一协议的意义，是把“我们做了一个系统”转化为“在相同条件下，系统相较基础方案产生了可复现的改进，并且改进原因可以被实验解释”。

## 2. 实验范围和数据集

本协议将评测分成三层，不混用结果：

| 层级 | 数据集 | 用途 | 是否用于横向对比 |
|---|---|---|---|
| 核心对比集 | `testdata/benchmark/closed_loop_cases.json` | 30 个高信息量案例，覆盖正常、语义安全、能力边界、恢复、安全停止和执行失败 | 是 |
| 完整回归集 | `testdata/benchmark/abcd_closed_loop_v1.json` | 64 个 A/B/C/D 全链路案例，验证完整回归和稳定性 | 否，作为最终回归证据 |
| LLM 留出集 | `testdata/benchmark/llm_generalization_v1.json` | 未参与提示词和规则调优的语言与组合泛化案例 | 只用于最终泛化验证 |

核心对比集的 30 个案例分布如下：

| 类别 | 数量 | 重点 |
|---|---:|---|
| `happy_path` | 10 | 多场景正常任务、目标绑定和组合动作 |
| `intent_safety` | 5 | 歧义、目标缺失、目标不存在、目的地不合法 |
| `capability_boundary` | 5 | 未覆盖动作、信息缺失和能力边界 |
| `recoverable_failure` | 3 | 动作级恢复和 TraceCoder 修复 |
| `safe_stop` | 2 | 重试耗尽后的安全停止 |
| `execution_failure` | 5 | 抓取、移动、释放等执行故障 |

所有变体必须使用同一份核心对比集、同一场景和同一故障注入配置。留出集不得用于调 Prompt、调规则或调阈值。

## 3. 实验变体定义

Baseline 是“比较对象”，消融是“去掉一个关键模块后的完整系统”。二者不能混为一谈。

| 变体 | 当前运行方式 | 保留内容 | 去掉内容 | 用途 |
|---|---|---|---|---|
| `V0_RULE_BASELINE` | `--mode baseline` | 规则意图、固定原子策略、Mock 执行 | CodeArts、智能意图、D 修复 | 传统固定流程基线 |
| `V1_CODEARTS_B` | `--mode codearts` | 规则意图、真实 CodeArts 策略、策略校验、Mock 执行 | A 的 LLM 解析、D 的 LLM 修复 | 证明 CodeArts 策略生成价值 |
| `V2_FULL_NO_D` | `--mode intelligent --variant V2_FULL_NO_D` | A、B、C 和安全校验 | D 诊断、patch 和重试 | 证明失败修复模块价值 |
| `V3_FULL_NO_GATE` | 需增加 `--variant no_gate` | A、B、C、D | 策略安全门禁 | 证明安全门禁价值，仅允许 Mock/Isaac 离线实验 |
| `V4_FULL` | `--mode intelligent` | A/B/C/D 全部链路 | 无 | 最终方案 |
| `V5_RAW_LLM` | 后续单独适配器 | 原始大模型动作输出 | 任务契约、稳定 ID、策略校验 | 直接大模型控制的对照组，可选 |

其中 `V3_FULL_NO_GATE` 只能在仿真中运行，禁止连接真实机器人。它的目的不是作为产品方案，而是量化说明“没有安全门禁会发生什么”。

当前运行器已经支持 `V0_RULE_BASELINE`、`V1_CODEARTS_B`、`V2_FULL_NO_D` 和 `V4_FULL`；`V3` 仍需后续增加“仅仿真、跳过安全门禁”的受控开关。

## 4. 必须固定的实验条件

每份报告必须记录以下条件：

| 条件 | 统一要求 |
|---|---|
| 代码版本 | 记录 Git SHA，实验期间不得修改代码 |
| 测试集 | 记录 manifest 路径和版本；案例顺序、案例 ID 不得变化 |
| 场景 | 同一 `scene_id`、物体布局、故障注入和场景版本 |
| 随机性 | 固定 `seed`；模型参数和采样设置保持一致 |
| 执行后端 | 横向对比统一使用 Mock；Isaac Sim 单独作为 HIL 证据 |
| 模型与策略 | 记录模型、CodeArts policy、Prompt/Skill 版本 |
| 重试 | 统一设置 transport retry、动作 retry 和 D 最大修复轮数 |
| 超时 | 所有变体使用相同的超时设置 |
| 重复次数 | 核心对比集建议 5 次；在线 CodeArts 至少 3 次 |
| 环境 | 记录 Python、依赖、操作系统和执行主机 |
| 数据泄漏 | 留出集不得出现在 Prompt 示例、规则模板和调参过程 |

在线 CodeArts 的真实性和离线横向可比性分开处理：

- 离线对比用于判断算法和模块效果，尽量使用固定输入和可复现 Provider Fixture；
- 在线 CodeArts 用于证明真实 Provider 已接入，并单独报告调用次数、错误、延迟和重试；
- 不能用一次在线调用结果与一组离线结果直接比较成功率。

## 6. 评价指标定义

### 6.1 主要指标

| 指标 | 计算方式 | 方向 |
|---|---|---|
| 合法任务成功率 | 预期为 `SUCCEEDED` 且最终成功的案例数 / 合法任务数 | 越高越好 |
| 语义目标准确率 | 目标 ID 和目的地 ID 均精确匹配的案例数 / 需要绑定的案例数 | 越高越好 |
| 危险任务误执行率 | 预期应阻断或澄清但实际进入执行器的案例数 / 危险案例数 | 越低越好，目标为 0 |
| 策略契约通过率 | 通过 `strategy.v1` 和策略安全校验的策略数 / 被检查策略数 | 越高越好 |
| 可恢复故障恢复率 | 预先标记为可恢复且最终成功的案例数 / 可恢复故障案例数 | 越高越好 |
| 安全停止正确率 | 预期 `SAFE_STOP` 且实际 `SAFE_STOP` 的案例数 / 安全停止案例数 | 越高越好 |
| 假成功率 | 结果声称成功但最终世界状态验证失败的案例数 / 声称成功案例数 | 越低越好，目标为 0 |
| 轨迹追溯完整率 | A/B/C/D 中 `task_id`、策略、执行、反馈均可关联的案例数 / 总案例数 | 越高越好 |
| 案例稳定率 | 同一案例重复运行的最终判定和关键 ID 均一致的案例数 / 总案例数 | 越高越好 |

### 6.2 性能和工程效率指标

```text
CodeArts provider latency: P50 / P95
端到端延迟：P50 / P95
平均人工介入次数
平均故障恢复时间
从需求到首次成功运行时间
新增任务的人工代码量
新增任务的调试轮数
```

“通过率”和“执行成功率”必须分开：安全阻断案例被正确阻断时，应计入任务判定通过，但不能计入执行器成功。

### 6.3 提升幅度

所有 PPT 对比同时给出百分点和相对变化：

```text
绝对提升 = 完整方案指标 - Baseline 指标
相对提升 = (完整方案指标 - Baseline 指标) / Baseline 指标
```

对于误执行率、人工介入次数和时延等“越低越好”的指标，使用：

```text
下降比例 = (Baseline 指标 - 完整方案指标) / Baseline 指标
```

当 Baseline 为 0 时，只报告绝对值和分子/分母，例如 `0/15`，不计算相对提升。

## 7. 标准执行流程

### 阶段一：冻结实验

1. 确认 Git SHA、依赖和配置；
2. 校验核心对比集和完整回归集；
3. 确认测试集没有出现在新增 Prompt 或规则中；
4. 生成唯一 `experiment_id`；
5. 将运行参数写入报告元数据。

实际操作时，先生成一个批次编号，再把同一个编号传给 V0/V1/V2/V4 的每次命令，例如：

```powershell
$experiment_id = "exp-20260828-01"
```

这样四份报告明确属于同一轮对比；如果没有传，运行器会自动生成编号，适合单独冒烟，不适合正式横向对比。

### 阶段二：运行 Baseline 和完整方案

离线规则基线：

```powershell
python tools/run_closed_loop_benchmark.py `
  --manifest testdata/benchmark/closed_loop_cases.json `
  --mode baseline `
  --policy planner `
  --repeats 5 `
  --output reports/experiment_v0_rule_baseline.json
```

完整智能方案：

```powershell
python tools/run_closed_loop_benchmark.py `
  --manifest testdata/benchmark/closed_loop_cases.json `
  --mode intelligent `
  --policy quality `
  --repeats 5 `
  --output reports/experiment_v4_full.json
```

去掉 D 的消融方案：

```powershell
python tools/run_closed_loop_benchmark.py `
  --manifest testdata/benchmark/closed_loop_cases.json `
  --mode intelligent `
  --variant V2_FULL_NO_D `
  --policy quality `
  --repeats 5 `
  --output reports/experiment_v2_full_no_d.json
```

真实 CodeArts 只用于 Provider 真实性证据，必须单独运行并单独保存报告：

```powershell
$env:CODEARTS_BENCHMARK_ALLOW_LIVE = '1'
python tools/run_closed_loop_benchmark.py `
  --manifest testdata/benchmark/closed_loop_cases.json `
  --mode codearts `
  --policy quality `
  --pure `
  --repeats 3 `
  --output reports/experiment_v1_codearts_online.json
```

### 阶段三：运行消融

在相同的核心对比集和故障注入下运行 `V2_FULL_NO_D`。`V3_FULL_NO_GATE` 目前只保留协议定义，等安全门禁的仿真隔离开关完成后再运行。所有消融结果必须标记为实验用途，不得作为产品默认配置。

### 阶段四：生成统计

统计程序必须同时输出：

- 每个变体的总体指标；
- 每个类别的指标；
- 每个案例的重复结果；
- 与完整方案的绝对差值和相对差值；
- 失败案例和原始证据路径；
- 是否存在数据缺失、环境不一致或 Provider 错误。

### 阶段五：冻结 PPT 数据

只有满足以下条件的数据才能进入正式 PPT：

- 原始报告存在且可回放；
- 所有运行使用同一协议版本；
- 没有把 Mock、CodeArts 在线和 Isaac Sim 混在同一成功率中；
- Provider 错误、网络错误和业务失败已分开统计；
- PPT 数字能回溯到案例 ID 和报告文件。

## 8. 建议验收门槛

完整方案的比赛展示目标：

| 指标 | 建议目标 |
|---|---:|
| 合法任务成功率 | ≥ 95% |
| 语义目标准确率 | ≥ 95% |
| 危险任务误执行率 | 0% |
| 策略契约通过率 | 100% |
| 假成功率 | 0% |
| 可恢复故障恢复率 | ≥ 90% |
| 安全停止正确率 | 100% |
| 轨迹追溯完整率 | 100% |
| 核心对比集案例稳定率 | ≥ 95% |

这些是展示目标，不得在结果尚未实测时写入成绩。若某项未达标，应在 PPT 中呈现为当前问题和下一步优化，而不是删除该指标。

## 9. 第 10 页 PPT 的数据映射

第 10 页只使用核心对比实验报告，不直接使用不同批次的零散成绩。

建议展示：

1. 左侧：`V0_RULE_BASELINE`、`V1_CODEARTS_B`、`V2_FULL_NO_D`、`V4_FULL` 的指标表；
2. 中间：合法成功率、故障恢复率、安全误执行率三组对比图；
3. 右侧：一个“失败 → D 诊断 → patch → 复验”的典型案例；
4. 页脚：案例数量、重复次数、后端、Git SHA、报告路径和实验日期。

页面结论必须使用以下句式：

> 在相同的 N 个案例、相同场景和相同故障注入条件下，完整方案相较 V0 基线在合法任务成功率上提升 X 个百分点，在故障恢复率上提升 Y 个百分点，并将危险任务误执行率控制为 0；消融结果表明，提升分别来自语义结构化、安全门禁和失败修复模块。

## 10. 下一步需要补充的代码能力

协议和 V0/V1/V2/V4 的基础运行入口已经建立，后续还需要：

1. 把 V3 的无门禁实验限制在隔离仿真后端；
2. 在真实业务题集中补齐目标 ID、目的地 ID 和世界状态验证字段；
3. 用在线 CodeArts 和 Isaac Sim 分别补充真实性与 HIL 证据，仍不与离线主对比合并；
4. 将多次实验报告汇总为 PPT 可用的 CSV/JSON，并保留失败案例证据。
