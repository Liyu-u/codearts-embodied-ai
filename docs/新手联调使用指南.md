# 具身智能系统统一联调仓库新手使用指南

> 适用对象：第一次参与本项目联调的四位成员
> 目标：让四个人的模块能够按照统一接口连接、测试、定位问题并逐步接入 Isaac Sim 或真机。
> 当前仓库：以 main 分支的统一联调骨架为准。

---

## 1. 先记住三句话

1. **先看协议，再写代码。** 所有模块之间传递的数据，必须符合 contracts/v1/ 中的 JSON Schema。
2. **模块之间只通过适配器连接。** 不要直接导入其他人的内部类、内部函数或私有文件。
3. **先 Mock，后仿真，最后真机。** 没有通过上一阶段的测试，不要直接连接 Isaac Sim 或真实机器人。

本仓库解决的是“如何把四个人的代码接在一起”，不是要求大家把所有代码都写在同一个文件里。每个人可以保留自己的实现方式，但必须提供统一的输入、输出和健康检查接口。

## 2. 四个人分别负责什么

项目有四个逻辑责任模块。C 同学同时负责感知和执行，因此仓库中会看到五个目录，但仍然是四个人协作。

| 负责人 | 逻辑职责 | 负责目录 | 输入 | 输出 |
|---|---|---|---|---|
| A | 意图理解与目标绑定 | modules/intent_understanding/ | 自然语言 + perception.v1 | task.v1 |
| B | CodeArts 策略生成 | modules/strategy_generation/ | task.v1 | strategy.v1 |
| C | 环境感知 + Isaac Sim/真机执行 | modules/perception/、modules/executor/ | 场景、strategy.v1 | perception.v1、execution.v1 |
| D | 评测、错误诊断与反馈 | modules/evaluator/ | execution.v1 | feedback.v1 |

完整数据流如下：

~~~text
用户指令
   ↓
C：感知模块 → perception.v1
   ↓
A：意图理解 → task.v1
   ↓
B：策略生成 → strategy.v1
   ↓
C：执行模块 → execution.v1
   ↓
D：错误诊断 → feedback.v1
   ↓
需要重试时，回到 A 或 B 修正任务/策略
~~~

## 3. 仓库目录怎么用

~~~text
contracts/                 # 唯一接口标准，所有人都要看
  v1/                       # 五种 JSON Schema

modules/                   # 各成员的模块代码
  perception/               # C：感知
  intent_understanding/    # A：意图理解
  strategy_generation/     # B：策略生成
  executor/                # C：执行
  evaluator/               # D：评测与反馈

integration/               # 跨模块编排，不放业务实现
  adapters/                 # 模块适配器
  config/                   # local/sim/real 配置
  pipeline.py               # 统一调用顺序

testdata/                  # 可重复的脱敏测试输入
  daily/                    # 日常场景
  industrial/               # 工业场景

tests/                     # 分层测试
  contract/                # 协议测试
  integration/             # 多模块联调测试
  e2e/                     # 端到端测试

docs/                      # 使用手册、决议和故障记录
~~~

## 4. 每个人要交什么

每个人至少要提交以下四类内容。

### 4.1 模块实现

放到自己的目录中：

~~~text
modules/<自己的模块名>/
~~~

例如 A 同学可以提交：

~~~text
modules/intent_understanding/parser.py
modules/intent_understanding/README.md
~~~

模块内部可以自行组织文件，但必须有一个清楚的入口文件，并在本模块的 README.md 说明：

- 模块用途；
- 输入格式；
- 输出格式；
- 启动方法；
- 依赖安装方法；
- Mock 使用方法；
- 已知限制。

### 4.2 适配器

适配器放到：

~~~text
integration/adapters/
~~~

适配器的作用是把个人代码包装成统一形式。最少提供：

~~~python
def run(input_json: dict) -> dict:
    """接收标准 JSON，返回标准 JSON。"""
    ...


def health() -> dict:
    """返回模块是否可以工作。"""
    ...
~~~

建议的文件命名：

~~~text
integration/adapters/perception.py
integration/adapters/intent.py
integration/adapters/strategy.py
integration/adapters/executor.py
integration/adapters/evaluator.py
~~~

适配器不应该重新实现业务逻辑。它只负责三件事：

1. 把标准输入转换成个人模块能理解的输入；
2. 调用个人模块；
3. 把个人模块输出转换回标准 JSON。

### 4.3 测试数据

每个人至少提供：

- 一个正常样例；
- 一个目标不存在或输入不完整的失败样例；
- 一个危险或应该被阻断的样例。

测试数据放到：

~~~text
testdata/daily/
testdata/industrial/
~~~

文件名建议带上模块名和用途，例如：

~~~text
testdata/daily/pick_red_cube.json
testdata/daily/target_not_found.json
testdata/industrial/collision_risk.json
~~~

测试数据中不得写入真实 API Key、真实机器人地址、个人电脑绝对路径或未经脱敏的运行日志。

### 4.4 测试和说明

测试放到对应目录：

~~~text
tests/contract/
tests/integration/
tests/e2e/
~~~

每个提交的 Pull Request 说明中必须写清楚：

- 修改了哪个模块；
- 使用了哪个输入协议和输出协议；
- 执行了哪些测试命令；
- 测试结果是什么；
- 是否有未完成事项。

## 5. 五个协议分别是什么

协议文件位于：

~~~text
contracts/v1/
~~~

### 5.1 perception.v1：感知结果

由 C 的感知模块输出，至少包含：

~~~json
{
  "schema_version": "perception.v1",
  "scene_id": "scene-001",
  "objects": [
    {
      "id": "obj-001",
      "category": "cube",
      "pose": {"x": 0.15, "y": 0.05, "z": 0.03}
    }
  ]
}
~~~

重点要求：

- 每个物体必须有稳定的 id；
- 坐标单位和坐标系要写清楚；
- 不确定的信息不要伪造，可以放在 attributes 或 execution 中说明；
- A 只能使用这个标准输出进行目标绑定。

### 5.2 task.v1：意图理解结果

由 A 输出，至少包含：

~~~json
{
  "schema_version": "task.v1",
  "task_id": "task-001",
  "action": "pick_and_place",
  "target_ids": ["obj-001"],
  "destination_id": null,
  "constraints": [],
  "status": "READY",
  "blocking_reasons": []
}
~~~

status 只能使用：

- READY：信息足够，可以交给 B；
- NEEDS_CLARIFICATION：需要用户补充信息；
- BLOCKED：存在安全问题或无法执行的问题。

如果 A 无法确定目标，不能随便猜一个物体，应该输出 NEEDS_CLARIFICATION 或 BLOCKED。

### 5.3 strategy.v1：策略结果

由 B 输出，至少包含：

~~~json
{
  "schema_version": "strategy.v1",
  "task_id": "task-001",
  "steps": [
    {
      "step_id": "step-001",
      "action": "pick_and_place",
      "arguments": {"target_id": "obj-001"},
      "on_failure": {"retryable": true}
    }
  ],
  "code": null
}
~~~

策略必须引用 task_id 和 target_ids，不能凭空生成一个感知结果中不存在的目标。

如果输出 Python 代码，代码必须经过安全检查，不能直接执行用户输入中的任意字符串。

### 5.4 execution.v1：执行结果

由 C 的执行模块输出，状态只能使用：

- SUCCEEDED：执行成功；
- FAILED：执行失败；
- SAFE_STOP：触发安全停止。

执行结果需要尽量保留：

- 每一步的结果；
- 轨迹点；
- 总耗时；
- 碰撞、超力、超速、急停等安全事件。

### 5.5 feedback.v1：错误反馈

由 D 输出，至少包含：

~~~json
{
  "schema_version": "feedback.v1",
  "task_id": "task-001",
  "diagnosis": "目标位置不可达",
  "retryable": true,
  "patch": {"suggestion": "重新选择安全放置位置"}
}
~~~

D 不应该直接修改 A、B、C 的内部代码。D 只输出事实、原因和建议，由对应负责人决定如何修复。

## 6. 四个人之间如何配合

### 第一步：先确定接口，不要先写复杂功能

四个人先一起确认：

- object_id 如何命名；
- 坐标单位是什么；
- 可执行动作有哪些；
- 什么情况算阻断；
- 错误码和重试规则是什么。

这些内容要先写进 contracts/v1/ 或 docs/，再写代码。

### 第二步：每个人先做本地 Mock

第一轮不要连接真实模型、Isaac Sim 或真机：

- C 用固定 JSON 模拟感知；
- A 用固定规则或简单模型输出任务；
- B 用固定模板生成策略；
- C 的执行模块用 Mock 返回成功或失败；
- D 根据 Mock 执行结果生成反馈。

目标是先让五段 JSON 能完整走通。

### 第三步：按顺序接入适配器

建议顺序：

1. C 提供 perception.v1 样例；
2. A 完成 task.v1；
3. B 完成 strategy.v1；
4. C 完成 execution.v1；
5. D 完成 feedback.v1；
6. 最后把适配器注入 integration/pipeline.py。

当前管线的调用关系是：

~~~python
task = adapters["intent"].run({
    "instruction": instruction,
    "perception": perception,
})

strategy = adapters["strategy"].run(task)
execution = adapters["executor"].run(strategy)
feedback = adapters.get("tracecoder")
~~~

如果 task.status 不是 READY，管线应该立即阻断，不再生成策略或执行动作。

### 第四步：再逐步替换 Mock

替换顺序建议为：

~~~text
规则 Mock
  ↓
真实意图理解
  ↓
真实策略生成
  ↓
Isaac Sim
  ↓
真机
~~~

每替换一个模块，都要保留上一阶段的测试数据，确保出现问题时能够判断是新模块还是接口问题。

## 7. 哪些内容可以改

以下内容可以由对应负责人修改：

- 自己负责目录下的业务代码；
- 自己的适配器；
- 自己的模块 README；
- 自己负责的测试数据；
- 自己负责的单元测试；
- docs/ 下的使用说明和故障记录；
- 在不破坏兼容性的情况下增加可选字段。

修改协议时，必须同时提交：

1. Schema 修改；
2. 正常样例；
3. 失败样例；
4. 契约测试；
5. 兼容性说明。

## 8. 哪些内容不能随便改

以下内容不能个人直接改完就合并：

- 删除或重命名 contracts/v1 中已有的必填字段；
- 改变 schema_version 的含义；
- 改变 task_id、物体 id 的关联规则；
- 把 READY、BLOCKED 等状态改成其他写法；
- 让模块直接依赖其他模块的内部路径；
- 绕过适配器直接调用其他人的代码；
- 把真实密钥、真机地址、个人路径提交到仓库；
- 在没有安全检查的情况下执行 LLM 生成的代码；
- 未经确认直接连接真机或发送真实运动指令；
- 为了让测试通过而静默修改输入数据；
- 删除别人的模块、测试、日志或文档。

涉及协议、安全规则、真机配置和公共管线的修改，应先在群里说明并获得四人确认。

## 9. 每次提交前怎么检查

进入仓库根目录后，依次执行：

~~~bash
make contract-test
make integration-test
make e2e
~~~

如果某个命令暂时没有测试，也要在 Pull Request 中明确写明“当前没有对应测试”，不能把没有测试当作测试通过。

提交前还要检查：

- 是否误提交 .env 或密钥；
- JSON 是否能被解析；
- schema_version 是否正确；
- task_id 是否贯穿全流程；
- 物体 ID 是否来自感知结果；
- 失败是否有明确原因；
- 危险任务是否能阻断；
- 是否能用 testdata/ 重新复现。

## 10. 推荐的分支和提交方式

每个人从 main 创建自己的功能分支：

~~~bash
git checkout main
git pull origin main
git checkout -b feature/<模块>-<功能>
~~~

例如：

~~~bash
git checkout -b feature/intent-parser-mock
git checkout -b feature/strategy-adapter
git checkout -b feature/executor-isaac
git checkout -b feature/feedback-schema-test
~~~

提交信息要说明做了什么：

~~~bash
git add modules/intent_understanding integration/adapters/intent.py tests/contract
git commit -m "feat: add intent understanding adapter"
git push -u origin feature/intent-parser-mock
~~~

然后创建 Pull Request。合并前至少需要：

- 修改人自测通过；
- 另一位成员看过输入输出；
- 契约检查通过；
- 没有密钥和个人路径；
- 说明已知限制。

## 11. 出现问题时怎么定位

按数据流从前往后查，不要一开始就怀疑 Isaac Sim：

1. 感知 JSON 是否能解析？
2. 物体是否有正确的 id、位置和类别？
3. A 是否输出了正确的 task_id 和 status？
4. B 是否引用了真实存在的目标 ID？
5. 策略是否符合安全约束？
6. 执行模块是否返回了标准状态？
7. D 的反馈是否说明了具体失败原因？
8. 能否用同一个 task_id 找到完整输入、输出和日志？

常见问题：

| 问题 | 常见原因 | 处理方式 |
|---|---|---|
| 找不到目标 | ID 不一致或 A 自己猜了名称 | 使用感知 JSON 中的 id，不要只传自然语言名称 |
| 管线直接阻断 | task.status 不是 READY | 查看 blocking_reasons，补齐信息或确认安全条件 |
| 策略无法执行 | B 使用了执行器不支持的动作 | 先确认动作清单，再生成策略 |
| 执行失败但无法重试 | execution.v1 缺少安全事件或步骤结果 | C 补充执行现场信息，D 再做诊断 |
| 本地能跑，联调不能跑 | 适配器输入输出没有遵守 Schema | 先跑契约测试，不要直接改管线 |
| 测试互相影响 | 使用了固定文件名或真实环境 | 使用独立 task_id 和 Mock 数据 |

## 12. 第一周建议目标

### 第 1 天：统一认识

- 四个人阅读本指南和 contracts/v1/；
- 确定模块负责人和目录；
- 确定 ID、坐标和状态的含义。

### 第 2 天：完成 Mock 输入输出

- C 提供感知样例；
- A 输出 task.v1；
- B 输出 strategy.v1；
- C 返回 execution.v1；
- D 返回 feedback.v1。

### 第 3 天：完成适配器

- 每个模块实现 run()；
- 每个模块实现 health()；
- 通过一条最简单的抓取/放置流程。

### 第 4 天：增加失败流程

- 目标不存在；
- 目标不可达；
- 碰撞风险；
- 执行失败后重试。

### 第 5 天：接入 Isaac Sim

- 先接入仿真；
- 保留同一份 Mock 测试；
- 对比策略、轨迹和安全事件；
- 暂不直接接真机。

## 13. 最终联调验收标准

满足以下条件，才算四个模块真正联调完成：

- 用户输入一句指令可以生成唯一 task_id；
- 感知、任务、策略、执行、反馈五种 JSON 可以依次传递；
- 每个模块都能通过适配器调用；
- 目标 ID 在全流程中不丢失；
- 不明确或危险任务可以阻断；
- 执行失败能生成可读的反馈；
- 失败可以使用同一个 task_id 复现；
- Mock 流程可以重复运行；
- Isaac Sim 流程通过后，才考虑真机；
- 四个人都能说明自己的输入、输出、测试和已知限制。

如果只完成了目录和 Schema，而没有模块实现、适配器和测试，只能称为“联调框架已建立”，不能称为“系统已联调完成”。
